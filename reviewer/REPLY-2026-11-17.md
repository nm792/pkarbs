## Why it happened (all six items)

Same root cause: the locked rule and the code were written as two separate deliverables (#373, #374) about 3 minutes apart, and nothing sat between them. Locking the rule was treated as the safeguard, but a rule only protects the test if something compares the code to it before it runs. Nobody was assigned to do that, so nobody did. The six items split into:

- Silent omissions (1 funding, 5 hour-of-day): the code did a simpler version of the rule and never flagged the gap.
- Silent substitutions (2 placebo scope, 4 weeks vs rows, 6 default 5 bp): a convenient implementation replaced the specified one. Items 2 and 6 matter most, because both change what the test can detect (cross-session placebo and a fallback spread both bias toward or away from an edge).
- Parameter drift (3, 5,000 vs 10,000 resamples): small, but it shows the rule text was not open while coding.

Common thread across the three rounds with design problems (register row 7): the test is built and run before anyone checks that it can tell an edge from no edge. Speed was prioritised (start the follow-up immediately), and the "does this discriminate" check was never a gate.

## What changes in how we work

1. No test runs until a rule-to-code table exists. For each line of the locked rule, one row: rule text, file:line that implements it, same/different. Any "different" is either fixed or written into the rule as a dated amendment BEFORE the run. Table lives next to the code.
2. Separate checker. The author does not sign off their own table. A second thread (or the Reviewer, if asked) fills the code column independently from the code only.
3. No silent defaults. A missing input (e.g. half-spread) must exclude the row and be counted in the output, never fall back to a constant. Output must print n excluded.
4. Discrimination check as a gate: before the real run, feed the code a synthetic series with no edge and one with a planted edge. It must return about zero and about the planted size. This addresses row 7 directly.
5. Rule and code are not merged within minutes of each other: the rule merges first and the code PR must cite the rule's commit hash.
6. Existing #374 results (none yet) must not be reported until the table in 1 passes. If these tests produced any number already, label it UNCHECKED.

## Coordination rule for the coordinator

"A locked rule is not a safeguard by itself. Before relaying any test result, confirm a rule-to-code table exists, was filled by someone other than the author, and shows no unamended differences. Missing = report UNCHECKED, not a result."
